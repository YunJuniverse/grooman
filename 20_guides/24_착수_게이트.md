# 24. 착수 게이트 — 정본·전제·해석 확인

> 일을 *시작하기 전에* 확인해야 하는 4가지. 2026-07 전 레포 월간 전수조사에서 **정본·전제 미확인(P5, 5개 repo)**이
> 최고 단일 비용군(ai-icons 195분 축 전면 반전·gamblescan 90분+80분·invest-ops 딜 메모 전면 재계산)으로 실증되어 신설(METH-124).
> 핵심 가치: **비싼 실수는 실행이 아니라 착수에서 만들어진다. 확인 질문 1개가 재작업 1일을 산다.**

---

## 1. 정본(SoT) 확인 — "무엇이 사실의 기준인가"를 사용자에게 묻는다

실사고: 하이웍스 조직도를 정본으로 *단정*하고 13개 티켓에 걸쳐 자기신고 데이터를 덮어씀 → 실제 정본은 반대 → 전면 역방향 재작업(ai-icons, 최대 단일 손실).

- **과거 사실을 기록하는 산출물**(RCM·장부·이력·실사)은 착수 전에 "무엇이 정본인가"를 사용자에게 확인한다 — 소스가 2개 이상이면 단정 금지.
- 정본과 실제가 다른 예외는 코드 주석·문서에 박제하고 이동 이력과 분리한다(재파싱 때 자동 복귀 방지).
- 기준 축을 바꾸면 그 축으로 계산하던 파생 지표를 전수 재해석한다 — 숫자는 맞는데 뜻이 없는 상태를 방지.
- 원자료 반입 즉시 당사자·소유관계·수신 성격을 확인한다(invest-ops: 미확인 프레이밍 위에서 1차 분석 전체가 무효). **이름이 비슷한 대상은 식별자로 고정**한다(신풍 vs 신풍제약 25분 — invest-ops).
- **repo 밖 정본(스프레드시트·게시 덱·폼·노션)은 편집 직전에 최신을 확인**한다 — 수정 시각(Drive `modifiedTime` 등)을 보고 남의 최신 편집 위에서 작업한다. 동시 편집으로 행이 밀려 30여 칸이 미반영된 사례(drip-chat-planning). **사본·내려받은 파일을 정본처럼 인계하지 않는다** — 개발 repo 가 받은 인계 파일의 이름과 내용 버전이 달랐다(비적용 팀 repo). 인계는 정본 링크 + 기준 시각으로.
- **사람이 AI 산출물을 직접 고쳤으면 그 수정을 보존하고 그 위에 패치**한다 — 라이브 사본의 해시를 대조해 사용자 수정분을 확인한 뒤 진행(drip-chat-planning «수정한 건 건들지 마»). 재생성으로 덮지 않는다.
- **«폴더 연결·작업 공간」 요청은 기존 repo 부터 찾는다** — 새 repo 를 만든다는 해석은 마지막(drip-chat-planning: 신설 오해석 즉시 철회).

## 2. 조사·문서의 진단은 착수 시점에 코드로 재확인한다

실사고: 조사 스냅샷의 "데이터원이 이미 존재, 호출만 하면 됨"·"아무것도 차감 안 됨" 진단이 둘 다 오진 — 그대로 착수했으면 오답 구현(gamblescan 2회 80분, repeat_of 연쇄).

- 스냅샷·인계 문서·이전 세션의 *진단*은 착수 시점에 실제 코드·데이터로 재검증한다. 문서는 낡는다 — 특히 "이미 있다/없다" 류 존재 판정.
- 증상 진단은 **확증 증거가 아니라 반증 대조군**으로 확인한다 — 가설에 맞는 증거 수집이 아니라 "정상이라면 이래야 한다"의 대조 실험(오진 2회를 코드 작성 전에 차단한 실례).
- 집계·라벨을 믿지 말고 산출 코드를 역추적한다("작성 인원 64"가 사람 수가 아니었음). **부재와 미포착은 다르다** — 회수 못 한 영역은 '없음'이 아니라 '불명'.
- **진단이 없으면 만든다** (METH-142). 「수준이 부족하다·개선해달라」류 모호 요청은 **해결책을 찾기 전에 현행 산출물을 실측**해 결함 목록부터 만든다. 실측 없는 도구·기법 리서치는 일반론으로 흐른다. 실사례: 웹게임 리서치 착수 전 프로토타입을 실측하니 소음이 유일한 실패 조건인 잠입 게임에 **오디오 0개·6.8MB 스프라이트 참조 0회·이동이 CSS transition** 이었다 — 이 7행이 결론을 「좋은 도구 목록」에서 「그림을 더 넣어도 안 오른다, 바닥 교체가 선행」으로 바꿨다(icons). §3 이 요청의 *범위*를 고정한다면, 이것은 요청의 *현황*을 고정한다.

## 2b. 버그 제보는 정해진 순서로 트리아지한다 (METH-147)

실사고(cafe24-renewal): 「크롬만·맥 사파리만·갤럭시만」 환경 한정 제보 3건이 **전부 실측 반증** — 실제 원인은 환경 무관. 외부(광고) 가설을 먼저 세워 자사 링크 전수 스캔을 미룸(60분) · 증상 부품을 서드파티로 단정(35분) · 제보 영상 속 결정 단서를 가설을 세운 뒤에야 발견(30분).

§2 반증 대조군의 **실행 절차** — 순서가 곧 규칙이다.
1. **URL·재현 조건부터 확보**한다. 없으면 가설을 세우지 않는다.
2. **제보자의 영상·캡처를 가설 전에 전수 판독**한다. 결정 단서는 대개 거기 있다.
3. **환경 한정어(«크롬만» 류)는 먼저 반증**한다 — 다른 환경에서 같은 증상이 나면 한정어는 제보자의 관측 범위였을 뿐이다.
4. **증상 부품의 출처를 식별**한다(자사 vs 서드파티). 단정하지 말고 로드되는 원본으로 확인(§4).
5. **싸고 결정적인 검사를 외부 가설보다 먼저** — 자사 전수 스캔은 10분, 외부 가설 검증은 반나절이다.
6. **한 제보 속 복수 증상은 분리**한다. 하나의 원인으로 묶으려는 유혹이 오진의 형태다.

## 2c. 대상 데이터의 실재·집합을 먼저 잰다 (METH-149)

실사고(gamblescan 7건 ~105분): 화면 숫자가 시드를 함께 셈 · 지표 열에 플랫폼별 수치가 섞여 첫 배치가 엉뚱함 · 접근 정책 때문에 캡처 0건 · 게시할 소재·현황 데이터 0건인 채 기능 착수 · 메타와 본문 배지가 서로 다른 게이트를 봄 · 메타 설명 77% 가 빈칸 생성문. 시드·기본값이 운영 DB 와 갈라져 출시 내내 응답이 잘린 사례(비적용 팀 repo, 생성 길이 상한).

- 데이터에 기대는 기능은 착수 전에 **대상 집합을 정의하고 실측**한다 — 행 수·분포·빈 값 비율·시드 포함 여부·누가 볼 수 있는가(권한 경로). §3b(이식 입력 실측)의 일반형이다.
- **화면 숫자 = 공개 목록과 같은 집합**인지 가드 테스트로 고정한다(gamblescan).
- 시드·픽스처 값과 **운영 값이 갈라질 수 있는 설정**(토큰 상한·요율·한도)은 운영에서 직접 읽어 대조한다.

## 3. 해석 계약 — 요청·시안의 해석을 첫 질문으로 고정한다

실사고: 시안을 "취사선택 참고안"으로 해석 → 오너 의도는 "정확 구현" → 전 항목 재대조(talmo 25분+별도 세션). "구조 텍스트는 코드 유지"로 좁게 그은 범위가 PM 의도와 어긋나 PR 재작업(tshome).

- **디자인 산출물 인계 시**: "정확 구현인가, 참고안인가"를 첫 질문으로. 
- **"관리 쉽게·개선해줘" 류 모호 요청**: 범위(어디까지)를 처음에 명시적으로 질의 — 좁게 긋고 재작업하는 것보다 싸다.
- **요청의 표면 진단을 코드로 반증한다**: "IR 관리가 어렵다" → 실제 갭은 딴 곳(이미 CMS 설계, 문제는 편집 주체). 요청 문면대로 착수하면 오답이 된다.
- 결정 질문을 던지기 전에 "어떤 답이 다른 질문의 전제를 깨는가"를 점검한다(선택지 전제 붕괴로 재수렴).

## 3b. 이식 요청은 착수 전에 입력 가용성부터 실측한다

실사고: "A 도 B 에 맞춰줘" 형태로 받은 점수 체계를 대상에 대보니 **입력 5축 중 가중치 60% 에 데이터가 아예 없었다**(분쟁 테이블이 다른 엔티티 전용·KYC 없음·보너스 없음). 그대로 만들었다면 같은 UI 에 정의가 다른 점수가 떠 **"비교 가능한 척하는 값"** 이 됐다(gamblescan).

- **겉보기엔 포팅이지만 입력이 없으면 그것은 새 정의를 만드는 일이고, 등급이 달라진다.** 이식은 Class A 로 보이고 새 정의는 Class B/C 다.
- 절차: ① 원본의 입력 축을 나열 ② 대상에 각 축의 데이터 존재·품질을 **실측**(존재 확인이 아니라 실값 — 지침 23 §1-4) ③ 부재분의 가중치 합을 계산 ④ 유의미하면 **Class C 로 에스컬레이션**하고 사람에게 "정의를 새로 만드는 일이 된다"고 알린다.
- 부분 이식으로 진행할 때는 **무엇이 원본과 다른 정의인지 산출물에 표기**한다 — 같은 이름의 지표가 다른 뜻을 갖는 것이 가장 비싼 오류다.

## 3c. 결정 대기 값은 코드·대외 산출물에 넣지 않는다 (METH-149)

실사고 계보(5개 repo): 요율이 하루 만에 바뀌었다 원복되고 시행일이 4회 이동 — 매번 운영 반영·재계산 SQL(비적용 팀 repo, 커밋 12건+) · ERP 화면 방식 18일간 4번 전환, 지운 기능이 2주 뒤 부활, «회계 안 함» 번복(icons-ax) · 정책 문서 시행 방식 10일간 4회 번복, 그중 3회는 같은 날 4시간 안(비적용 팀 repo) · 예매번호 형식이 하루 4번 바뀌어 PR 4건(lifeManager) · AI 가안 일정이 [가안] 표기 없이 대외 덱으로(drip-chat-planning). 공통점: **미확정 값이 확정 값의 자리에 먼저 들어갔다.**

- **상태 범례를 산출물에 단다** — `[확정]`·`[가안]`·`[검토안]`·`[협의]`(drip-chat-planning 운영방안 L13). 개발 인계 문서도 이 상태를 **승계**한다.
- **결정 대기 값은 설정·플래그로 격리**하고, 대외 산출물(덱·공지·약관)에는 넣지 않는다(지침 05 §9, 메모리 «대외 산출물에 가안 수치 금지»의 상류화). «결정 대기 항목까지 제안값 그대로 적용» 지시를 받으면 **그 목록을 되읽어 확인**한다 — 그 뒤 3일간 재조율이 따른 사례가 있다.
- **결정이 바뀌면 산문 괄호가 아니라 ADR supersede 체인**으로 남긴다(«10-19 — 11-03 에 바뀜» 괄호만 남은 icons-ax). 가격·법무·공개 메시지의 번복은 Class C — 같은 날 재번복이면 멈추고 사람 확인.
- **형식·규칙은 예시로 받는다** — «예매번호 형식» 같은 요구는 산문 대신 예시 3개를 먼저 받으면 4회 왕복이 1회가 된다(lifeManager 프롬프팅 교정안).
- **결정 수집은 번호 질문 + 추천 선명시**로 한 번에 묻는다(gamblescan:ADR-0036 · drip-chat-planning 시트 «회의 질문지» 탭 51문항).
- 기획→개발 인계에서는 개발 측이 **«넣지 않은 것과 까닭」·«정책안 안에서 맞지 않던 곳」을 역보고**한다(비적용 팀 repo 9건) — 지침 09 의 개발 측 슬롯.

## 4. 사용자가 그은 경계는 거절 전에 원문으로 검증한다

실사고: 사용자의 "평점 말고 공개된 사실만" 구분을 검증 없이 2회 거절 → robots.txt를 끝까지 읽으니 거절 근거가 부정확 → 그 사이 대안 작업이 90분 손실 + 덮어쓰기 사고(gamblescan, 단일 최대).

- 사용자가 스스로 경계·근거를 제시하면(이건 되고 저건 안 된다), 거절하기 전에 **1차 출처를 직접 열어 확인**한다. 검색 요약·기억은 뉘앙스를 뭉갠다.
- 판정을 표에 ❌로 적기 전에 공식 사이트·원문을 직접 연다(오픈뱅킹 "개인 불가" 오판 실례).
- 확인하지 않은 플랫폼 동작을 단정해 안내하지 않는다(GitHub base 리타깃 오안내 → 사용자가 안내대로 했는데 사고).
- **블랙박스 위젯·앱의 동작·파라미터는 문서 추측보다 실제 로드되는 JS·CSS 원본을 받아 읽어 확정한다** (METH-147). 배너 앱의 토큰 치환 조건을 문서로 두 번 헛짚다 설치 스크립트에서 확정(60분) · 리뷰 앱 스크립트 문자열에서 API 경로군·필수 파라미터까지 확정해 반나절 만에 데이터원 교체(cafe24-renewal). 그 과정에서 **비공식 API 를 쓰게 되면 실패 시 기존 경로로 떨어지는 폴백과 롤백 스위치를 필수**로 둔다.
- **외부 에이전트·CLI 의 능력은 문서나 추정으로 단정하지 않고 스크래치 폴더에서 헤드리스로 한 번 실행해 확인한다** (METH-148). 실사례(icons): 다른 에이전트 CLI 가 이미지 생성을 못 한다고 오판해 **사용자에게 API 키(비밀)를 요구**했다 — 한 번 돌려 봤으면 필요 없는 요구였다.

## 4b. 규칙·금지를 쓰기 전에 정본을 읽는다 (METH-142)

실사고: 한 세션에서 같은 유형이 세 번 났다 — 상위 결정을 인용하며 **범위를 넓히고 「재확인」이라 서술**, 대상의 정본 규칙을 안 읽고 배제, 근거가 ADR에 없는 **자체 가드레일을 정본처럼 인용해 사용자 요구를 금지로 단정**(icons).

- **인용은 원문 범위 안에서만.** 상위 ADR·결정을 근거로 삼을 때는 그 원문을 열어 적용 범위를 확인한다. 상위가 「게임 한정 금지」인데 하위에서 「어떤 지표에도」로 넓히고 재확인이라 적으면, 정당한 용법을 막으면서 **근거가 있는 것처럼 보인다** — 넓힌 사실이 문서에서 사라지기 때문에 가장 나쁜 형태다.
- **금지를 쓸 때는 적용 범위를 명시한다.** 범위 없는 금지는 다른 정본과 충돌한다(무조건 단독 불가 규칙이 구매 동봉 케이스를 위반 상태로 만들 뻔했다).
- **인용은 원문 문장 또는 §번호까지** (METH-147). 「(icons:ADR-0011)」 식 괄호 인용은 원문 문장을 그대로 옮기거나 §번호를 붙인다. 요약이 원문을 대체하고 **자기 인용이 권위를 얻는** 것이 드리프트의 구조다 — icons 한 세션 3건: 「icons:ADR-0029 폭발 그래프 금지」(실제는 슬롯·릴만) · 「체험 = 무상」(원문은 유상 축) · 「icons:ADR-0011 실력이 확률을 바꾸지 않는다」(**존재하지 않는 조항, 원문과 정반대** — 그 문장이 설계 결론을 떠받치고 있었다). 셋 다 사용자가 물어봐야 원문을 열었다. wrap 이 변경 문서의 ADR 인용을 파일 존재로 기계 검사한다(경고). **다른 repo 의 ADR 은 `<repo>:ADR-NNNN` 으로 표기한다** — 이 저장소의 ADR 과 구분되고, wrap 의 인용 검사가 이 저장소 파일만 대조한다. **상류 방법론의 공유 문서(지침·CLAUDE.md)가 상류 ADR 을 인용할 때도 `methodology:ADR-NNN`** — 다운스트림에서 보면 남의 repo ADR 이고, 같은 번호의 자기 ADR 과 섞이면 안 된다. 형식 예시는 인라인 코드로 감싼다(검사 대상 아님).
- **스냅샷의 「근거·참조」 섹션은 포인터만 둔다** — 해석을 본문에 섞지 않는다. 해석은 본문에서 «내 판단»으로 표지한다.
- **정본에 없는 자체 가드레일로 사용자 요구를 거절하지 않는다.** 거절 근거로 규칙을 인용하기 전에 그 규칙이 ADR·지침에 실제로 있는지 확인한다. 없으면 그것은 규칙이 아니라 이번 세션의 의견이다 — §4(사용자가 그은 경계는 원문으로 검증)의 *쓰기* 측 대응물.

## 5. 착수 전 체크 (요약)

작업 유형별로 해당 항목만 — 전 항목 기계 적용이 아니라 *비싼 실수의 길목*만 지킨다:

| 상황 | 착수 전 질문 |
|---|---|
| 과거 사실 기록물·다중 소스 | 무엇이 정본인가? (사용자 확인) |
| 문서·스냅샷 기반 착수 | 그 진단, 지금도 코드에서 참인가? |
| 시안·디자인 인계 | 정확 구현인가 참고안인가? |
| 모호 요청("쉽게·개선") | 범위는 어디까지인가? |
| 사용자 경계 제시 | 원문 확인했는가? (거절 전 필수) |
| 증상 디버깅 | 반증 대조군은 무엇인가? |
| 데이터 기반 기능 | 대상 집합·행 수·권한 경로를 쟀는가? (§2c) |
| 미확정 값이 걸린 요청 | 그 값은 [확정]인가? 아니면 플래그로 격리 (§3c) |
| repo 밖 정본 편집 | 지금 최신인가? 내가 고친 뒤 내려받아 diff 했는가? |
